# Policy sensitivity analysis

## Purpose

`overall` and `over` have two different roles and should not be collapsed into one post-hoc scalar.

1. **Continuous scientific outcomes**
   - `overall`: fraction of target area already processed.
   - `over`: processed area outside the target, normalized by target area.
   - These remain continuous quantities when comparing model families. For example, a shock-informed controller can be scientifically better if it achieves larger overall coverage while keeping over-removal lower, even when neither case crosses a particular target-reached threshold.

2. **Hard runtime policy**
   - `overall_removal_target` decides when the target is sufficiently covered to STOP as `target_reached`.
   - `over_removal_limit` is a fail-closed irreversible-removal limit. It also defines whether each of the 27 candidate actions is safe.
   - `no_safe_action -> STOP` remains fixed.

Therefore threshold choice is evaluated by sensitivity analysis, while continuous overall/over results remain available separately for scientific interpretation.

## Why the previous replay CSV alone is insufficient

`control_policy_replay.csv` stores the decision under one threshold pair (currently 0.95 / 0.05), but not every candidate's cost and over-removal fraction. Changing `over_removal_limit` changes:

- which candidates are safe,
- whether `no_safe_action` occurs,
- which safe candidate is selected,
- whether an estimated-selected action would be unsafe under the oracle-current branch.

V1.12 therefore performs one additional GPU pass and caches threshold-independent metrics for all 27 candidates. Every threshold pair is then evaluated from the **same fixed predictions**, avoiding repeated inference noise.

## Default grid

- overall threshold: `0.70 0.75 0.80 0.85 0.90 0.95`
- over limit: `0.03 0.05 0.075 0.10 0.15 0.20`

This range is exploratory. It does **not** mean that 20% over-removal is acceptable in the real experiment.

## Smoke run

From `adaptive_control_runtime/`:

`python validation\policy_sensitivity_analysis.py --runtime-config adaptive_runtime_config.yaml --max-states-per-pulse 5`

## Full run

`python validation\policy_sensitivity_analysis.py --runtime-config adaptive_runtime_config.yaml`

The first run creates:

`<session_root>/offline_evaluation/policy_sensitivity_YYYYMMDD_HHMMSS/policy_candidate_cache.npz`

The cache includes current-state fractions and all-candidate cost/overall/over arrays for both:

- estimated-current controller
- oracle-current controller

The oracle-current definition is identical to the end-to-end replay: only the current mask is replaced by the measured mask. Transition B keeps the same State-Estimator `z_shock`.

## Reusing an existing cache

To try another threshold grid without GPU inference:

`python validation\policy_sensitivity_analysis.py --runtime-config adaptive_runtime_config.yaml --reuse-cache --cache "F:\...\policy_candidate_cache.npz" --overall-thresholds 0.80 0.85 0.90 --over-limits 0.05 0.075 0.10`

## Main outputs

- `continuous_current_fraction_summary.csv`
  - threshold-independent overall/over estimation accuracy by model.
- `continuous_current_fraction_by_target.csv`
  - the same quantities for each of the eight target shapes.
- `policy_grid_summary.csv`
  - aggregate threshold sensitivity for each model.
- `policy_grid_by_target.csv`
  - target-specific sensitivity.
- `policy_grid_by_pulse.csv`
  - pulse-dependent sensitivity.
- `current_policy_comparison.csv`
  - written when the currently configured threshold pair is included in the sweep.
- `plots/`
  - heatmaps for decision agreement, false CONTINUE, oracle-unsafe estimated actions, and target-reached rate.

## Key fields to prioritize

For live-policy selection, do not maximize target-reached rate alone. Historical test trajectories were generated by the fixed data-collection policy, not by an adaptive controller aiming at the eight targets.

Prioritize:

- `false_continue_fraction`
  - estimated controller CONTINUE while oracle-current controller STOPs.
- `false_continue_due_oracle_over_fraction`
  - especially important because processing is irreversible.
- `estimated_action_oracle_unsafe_fraction_on_both_continue`
  - both controllers continue, but the action chosen from the estimated state violates the oracle-current over limit.
- `false_stop_fraction`
  - too-conservative policies can stop useful processing prematurely.
- `selected_action_match_fraction_on_both_continue`
  - exact action identity.
- `oracle_regret_*_when_est_action_oracle_safe`
  - how costly an action mismatch is when the estimated-selected action remains safe under the oracle-current branch.

The target-specific table is required before freezing one common threshold pair because small/narrow targets can be disproportionately affected by an area-normalized over-removal ratio.

## Interpretation for model comparison

Hard STOP thresholds are operational policy parameters. They should not replace the continuous morphology comparison.

A scientifically useful model comparison can therefore report both:

- continuous overall / over behavior and morphology prediction metrics, and
- safety/completion behavior under the frozen runtime stop policy.

This keeps the claim "shock-informed control improves target coverage while reducing excess removal" conceptually separate from the engineering choice of when the controller must stop.
