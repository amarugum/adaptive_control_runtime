# PC2 Policy v1.0 integration (2026-10-13)

## Applied control specification

The **live PC2 runtime**, not merely the offline analysis, now uses Policy v1.0.
The four model modes share the same decision logic.

- Binary processing convention: 1 = removed/processed, 0 = not removed.
- Current and candidate masks use `action_selection.candidate_threshold` (0.5).
- Target is a fixed, registered 256 × 256 binary mask; **no translation or registration during scoring**.
- Overall coverage: `C=|S∩T|/|T|`; over-removal: `O=|S\T|/|T|`.
- Predicted positive increments: `ΔC=max(C_next−C_current,0)`, `ΔO=max(O_next−O_current,0)`; **no reward for apparent predicted shrinkage**, matching `validation/combined_stop_policy_validation.py`.
- Score: `L(a)=3 ΔO(a)−ΔC(a)`; minimize over feasible candidates; epsilon absent.
- Candidate feasible **only if** `predicted O_next < 0.10` (strict).
- Candidate continuation criterion: `min_safe L < 0` (strict).
- Current-state STOP: `O_current >= 0.10` has priority over `C_current >= 0.90`, then maximum steps (minimum of the server-side and request-side limits).
- Maximum 20 control steps per hole remains a server-side upper bound. Stage 2 considers 27 candidate actions; each action is applied for 5 pulses on PC1.
- Offline scripts using historical L1+Dice are intentionally **not automatically migrated**. For live decisions inspect `candidate_scores.csv` and `response.json`.

## STOP stages, reasons, and result schema

| Stage | Condition | `decision` | `stop_reason` | `best_action` |
| --- | --- | --- | --- | --- |
| State Estimator | `O_now >= 0.10` | `stop` | `over_removal` | `null` |
| State Estimator | `C_now >= 0.90` and over has not triggered | `stop` | `target_reached` | `null` |
| State Estimator | Step cap reached | `stop` | `max_control_steps` | `null` |
| Transition | No candidate with `O_next < 0.10` | `stop` | `no_safe_action` | `null` |
| Transition | All feasible candidate losses `L >= 0` | `stop` | `nonpositive_utility` | `null` |
| Transition | Feasible best `L < 0` | `continue` | `null` | Chosen candidate |

All stop responses have `status=ok` and `decision=stop`. Runtime errors instead carry `status=error`, HTTP 500; **PC1 must treat them as non-execution**.

The `/v1/decision` protocol version remains `1.0`. `best_action` retains identifiers and movement/energy fields; a continuation additionally contains:

- `predicted_policy_loss` = `L` (normally negative for executable candidates).
- `predicted_utility` = `-L`.
- `predicted_delta_overall`, `predicted_delta_over` (clamped positive increments).
- `predicted_cost` is retained for backwards API shape, but its **meaning changes** from L1+Dice to `L`, so it may be **negative**. PC1 GUI displays or validations must not assume `predicted_cost >= 0`.
- Response `policy` contains version, lambda, target and over limit. `/v1/health` also reports them.
- For stage-2 decisions, `candidate_evaluation.best_policy_loss` and `best_predicted_utility` are diagnostic even on `nonpositive_utility`. `candidate_scores.csv` includes raw and clamped increments, safe flag, rank, and selection.

`status=ok, decision=continue` is **only an action proposal**. PC1 retains sole authority to execute the laser. Errors, missing/unknown decision fields, discrepancies, and communication failure must fail closed (e.g., DG645 SINGLE and no automatic retry).

## PC1 integration checklist (PC1 source not provided in the three ZIP files)

1. Confirm the PC1 client handles `stop_reason='nonpositive_utility'` as terminal STOP, without trying to access `best_action`.
2. Confirm *every* `decision='stop'` (including `target_reached`) results in no further laser pulses for that hole; `best_action=null` may occur. Distinguish success from `no_safe_action` / `over_removal` in logs/UI.
3. Confirm `status!='ok'`, malformed JSON, timeout, HTTP error, policy mismatch, or unknown `decision` produces an immediate safe stop with **no retries of irradiation**.
4. Confirm UI/logging accepts a **negative** `best_action.predicted_cost` or switches to `predicted_policy_loss` / `predicted_utility`.
5. Check the PC1-specified `max_control_steps` and UI labels; PC2 additionally caps at 20. Action set and command semantics are unchanged.
6. Prefer checking `/v1/health.policy` matches `v1.0 / delta_area_v1 / λ=3 / overall=.90 / over=.10` before a run.
7. Run shadow with the laser blocked first, then human-approved experiments. **The over limit is a model-based quality gate, not a physical safety guarantee**; earlier offline analysis found systematic underestimation of over-removal.

Without the actual PC1 source, the above is a required compatibility review, not a claim that PC1 has been checked or edited.

## Safe deployment on PC2

1. Back up current `adaptive_control_runtime`. Stop the PC2 server before replacing files.
2. Unpack the *changed-only* ZIP at the parent of `adaptive_control_runtime` (preserving the inner `adaptive_control_runtime/` folder) or use the complete reference ZIP. Review `adaptive_runtime_config.yaml` before replacing local custom settings. The supplied active YAML preserves the uploaded `session_root`, model checkpoints, resources, ORCA settings and GPU performance settings; only action and STOP policy values changed.
3. From `adaptive_control_runtime` run `python -m pytest -q` (tests do not use actual model weights or physical hardware).
4. Run `python init_storage.py --config adaptive_runtime_config.yaml` if starting a new session; then `python smoke_test_models.py --config adaptive_runtime_config.yaml` and `python smoke_test_decision.py --help` for syntax. The latter requires a running server and saved ORCA data; do **not** interpret passing tests as authorization for laser irradiation.
5. **Use a new `experiment_id`** for Policy v1.0. Experiment snapshots are immutable. Reusing an existing experiment ID whose `runtime_policy.json` still refers to L1+Dice or the old thresholds triggers `EXPERIMENT_RUNTIME_POLICY_CONFLICT` by design.
6. `/v1/health` should report the new policy. Perform end-to-end no-laser Shadow smoke with PC1 and examine `response.json`, `candidate_scores.csv` and the saved experiment policy snapshot.

## Files changed

- `runtime/selector.py`: live scoring and safe candidate selection (legacy offline `candidate_table` retained for tooling).
- `runtime/decision_policy.py`: fail-closed on `no_safe_action` or `nonpositive_utility`.
- `runtime/engine.py`: use Policy v1.0, emit policy metadata, enforce max step on PC2, reject nonfinite state outputs.
- `runtime/config.py`: validate new scoring method and parameters; reject legacy L1+Dice-only settings.
- `adaptive_runtime_config.yaml`, `adaptive_runtime_config.example.yaml`: set λ=3 / overall=.90 / over=.10; no epsilon or spatial divisions.
- `server.py`: expose policy parameters on health endpoint.
- `smoke_test_decision.py`: label displayed score as `L` rather than legacy `J`.
- Policy unit/integration tests and docs.
